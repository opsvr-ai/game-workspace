# 看门狗即控制面（Watchdog as Control Plane）—— 落地价值分析与改造方案

> 2026-10-03。背景是这一天的全站实测：**26 台里 23 台台账写着 `remoteReady=true`，实际进不去**。
> 老板提出：与其每台单独做配置，不如把「远程控制」整体收到看门狗里 —— 看门狗本来就是
> 管理员权限安装的守护进程，负责主进程重启、升级、健康验证。本文回答「值不值得、怎么落」。

## 一、结论

**值得做，而且应该把它当成唯一控制面（single control plane）来做。**
理由不是「省事」，而是今天的实测证明**逐台配置这条路在工程上不成立**（见第二节），
而看门狗通道在所有会上报的机器上**已经可用且已验证**（见第三节）。

一句话方案：**看门狗只长「通用原语」，不长业务逻辑**；远程控制脚本（体检 / 修复 / 传文件 /
取日志 / 截图）作为**服务端目录里的脚本**下发执行，客户端、客服端的更新与验收也由它闭环。
这样终端上**零配置**：不开管理共享、不开 RPC/WMI/WinRM、不装第三方远控、不改登录习惯。

## 二、为什么「逐台配置」不成立（今天的实测）

| 失败模式 | 实测证据 | 逐台配置能不能解 |
|---|---|---|
| 策略写了不生效 | 13 台 `LocalAccountTokenFilterPolicy=1`（REG_DWORD），但网络登录令牌仍被降级：安全日志 4624 `elevated=否`（能进的 179=是） | **要重启**才生效（124 重启后 `elevated=是`，已证实）→ 每台都得停一次业务 |
| 共享根本不存在 | 192.168.0.197 `autoShareWks=0`，只有 `IPC$` → `STATUS_BAD_NETWORK_NAME` | 能解，但每台都要单独查 |
| 整段网段不可达 | 8 台 `PC-*`：运维机与 179 都 ping/445/135 不通，而它们自己 445 在听、防火墙全关 → 路由隔离 | **解不了**，除非动网络 |
| 运维机自身 | `ForceGuest=1`（仅来宾共享模型），`Policies\System` 下只剩一个 `LocalAccountTokenFilterPolicy` | 要单独修 |
| 台账不可信 | `remoteReady` 只代表「开通脚本跑过并自检通过」，**从不做外部实测** | 语义问题，不是配置问题 |

代价：每台要么人工到场、要么重启打断陪玩；26 台的往返成本是**小时级 × 每轮**，
而且**每加一台机器就再来一次**。相比之下，看门狗任务通道今天在 116/124 上完成了
读注册表、重启 SMB 服务、下发并回收报告、重启机器 —— **没在任何一台机器上做前置配置**。

## 三、看门狗已经具备的能力（来自 `apps/watchdog-service/main.go`，2489 行）

- **服务化**：`install` / `remove` / `run`，SYSTEM 权限，开机自启（`installService`）。
- **自升级**：云端 30 分钟探测构建号 → 分阶段替换 + 计划任务重启自己（`cloudSelfUpdateCheck`、
  `stageSelfReplace`、`scheduleSelfRestart`）；换不掉时留 `.old` 下次继续（实测 125 就是靠重启完成的）。
- **客户端全生命周期**：发现（陪玩端/客服端多路径）、**在用户会话里拉起**（`launchInUserSession`，
  WTS + CreateProcessAsUser）、崩溃守护、单实例接管、快捷方式修复（`repairClientInstall`）。
- **客户端更新**：下载整包 → 校验 → 原子替换 → 旁路安装 → 健康判定（5 分钟期限）→ **失败回滚 + 版本黑名单**
  （`applyUpdateAtomic`、`installSideBySide`、`healthMatches`、`rollbackUpdate`、`blockVersion`）。
- **上报与诊断**：机器台账上报（含构建号、远程就绪自检）、`reportDiag` 落盘、心跳文件。
- **远程任务**：`GET /api/agent/machine-tasks`（60 秒一轮）+ `runRemoteTask`（script / command），
  输出回传 `POST /api/agent/machine-task-result`。

也就是说：**更新、重启、健康验证这三件事它本来就干了**；缺的只是「通用远程控制原语」。

## 四、缺口 → 本次补的四个通用原语（已实现，未发布）

| 原语（`mode`） | 作用 | 替代了什么 |
|---|---|---|
| `urlscript` | 服务端给 URL + sha256，下载校验后当脚本跑 | 4000 字符上限、往公网 `/uploads` 丢脚本 |
| `fetch` | URL → 本机指定路径（可备份、原子替换） | 往目标机**推送文件**（原本要 C$/SMB） |
| `send` | 本机指定路径 → 服务端 `uploadUrl` | 从目标机**取文件**（日志/报告/截图，原本要 C$） |
| `usersession` | 在**登录用户会话**里执行命令，输出重定向回传 | 截屏、UI 操作、用户态程序（SYSTEM 会话干不了的） |

附带：
- **领任务节奏 60 秒 → 20 秒**（远程操作从「等一分钟」变成「等二十秒」；26 台 ≈ 78 次 GET/分钟，可忽略）。
- **sha256 强制校验**（服务端给了就必须对上）、**单文件 64 MB 上限**、`fetch` 先下 `.dl` 校验通过再原子替换
  （第一版会「先落盘再校验」，校验失败会在目标机留坏文件 —— 单测已钉住）。
- `%TEMP%` 这类 Windows 变量展开（`os.ExpandEnv` 不认百分号语法，单测抓到的）。

## 五、还需要的能力（分三层，按性价比排序）

### 批次 A：服务端/管理端（不需要动终端，随时可上）
1. **脚本目录（ops-scripts）**：把 `probe-watchdog` / `fix-watchdog` / 就绪性自检 / 清理 / 传文件
   注册成**带名字和 sha256 的脚本**，管理端点「体检 / 修复 / 取日志」即可下发 `urlscript`。
2. **文件回传接口**：`POST /api/agent/machine-file`（共享令牌）+ 管理端下载，配合 `send`。
3. **台账 `remoteReady` 改成「实测通过」**：由机器自己的**回环网络登录自检**产出
   （今天已验证：用 chunlvops 显式凭据连 `\\127.0.0.1\C$`，安全日志 4624 的 `elevated` 与外部实测一致），
   而不是「脚本跑过」。顺带修掉「23 台假就绪」。
4. **`can-reboot` 接口**：服务端知道有没有在接单/在打游戏，看门狗问它才决定重启；
   于是「重启才能生效」的那些机器可以**自动挑空闲时间重启**，不用人工排期。

### 批次 B：看门狗（需要发终端更新 —— 必须先问老板）
5. **就绪性自检 + 自愈**：策略值（`LocalAccountTokenFilterPolicy`/`ForceGuest`）、
   `AutoShareWks` + `C$` 重建、445 放行按需修复，然后**回环复测**并把结论写回台账。
   这一条直接消灭「23 台假就绪」里能自愈的部分。
6. **空闲感知重启**：结合 `can-reboot` + 本机游戏/客户端进程判断，只在真空闲时重启。
7. **任务签名**：现在任务只靠一个硬编码共享令牌。一个能执行任意 SYSTEM 命令的通道，
   应该：每台一机一密、任务带 HMAC 签名与时限、脚本 sha256 白名单、执行审计落盘。
8. **长轮询/更长连接**（可选）：把 20 秒轮询降到秒级延迟；任务少时省电、任务多时快。

### 批次 C：验收闭环（配合客户端/客服端发版）
9. **更新后的功能验收**，不只是「进程在跑 + 版本对」：
   - 本机侧：healthy 标记新鲜度、进程存活、窗口存在（`usersession` 可判定）、无崩溃循环；
   - **服务端侧**：新增 `GET /api/agent/machine-health?machineId=`，返回
     `{socketConnected, lastHeartbeatAt, lastOrderAt, versionOk}`；看门狗在健康窗口内
     拿它当验收依据，不通过就沿用现有 `rollbackUpdate` + `blockVersion` 回滚。
10. **回归测试脚本目录**：把「能登录 / 能看单 / 能抢单 / 能发消息」做成可下发的只读探针脚本，
    发版后按机器抽样跑，结果写台账。

## 六、价值量化（说人话）

| 维度 | 逐台配置 | 看门狗控制面 |
|---|---|---|
| 铺一台新机器的人工 | 到场/远程配置 + 视情况重启 | **0**（装好看门狗即完成） |
| 一次全站修一遍 | 26 台 × 数分钟 + 打断陪玩 | 一条目录任务，空闲时自动跑 |
| 攻击面 | 开 C$/ADMIN$、RPC、WinRM，共用管理员口令，第三方远控常驻 | **不开任何入站端口**、不发管理员口令、可去掉向日葵/ToDesk |
| 台账可信度 | 「脚本跑过」= ready（今天证明不可信） | 「回环实测 + 服务端验收」= ready |
| 可测试性 | 靠人工点 | 脚本目录 + 结果回传，**可回归、可审计** |
| 与业务的耦合 | 每台一份配置，越铺越乱 | 一套脚本，改一次全站生效 |

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 看门狗成为「一击全控」的高价值目标 | 批次 B-7：一机一密 + HMAC 签名 + 时限 + 白名单 + 审计；令牌不落客户端、只落服务端 |
| 自升级把服务换坏（引导问题） | 已有分阶段替换 + 失败留 `.old` + 计划任务重启兜底；发布前必须真机验证一次「换自己 + 重启」 |
| 任务通道被误用（脚本改线上业务开关） | 脚本目录 + 代码评审 + 只读优先；`blacklist.enabled` 之类业务开关**永不**由脚本触碰（AGENTS.md 规则 6） |
| 自动重启打断接单 | 只走 `can-reboot` 接口（服务端按订单状态判定）+ 本机进程判定 + 只挑空闲窗口 |
| 版本号不递增导致升不上去 | 本次构建号 2026100301 → **2026100302**；发布顺序：先上服务端接口，再发看门狗 |
