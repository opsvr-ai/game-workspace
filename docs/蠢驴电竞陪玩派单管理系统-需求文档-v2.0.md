## 0. 定位、优先级、铁律

### 0.1 这个系统是什么

- **形态**：SaaS。一套系统同时服务 **直营店**（老板自己的店）和 **租赁店 / 加盟店**（每家一个租客账号，数据互不可见）。
- **对外人设**：**散陪人设** —— 每个陪玩对外是「独立个人」，客户**感知不到工作室的存在**。所有界面、话术、称呼都必须守住这条。
- **开发者的身份**：系统开发者同时是超级管理员，拥有全部门店全部数据。
- **终极目标（2026-09-20 明确）**：**先把线下陪玩店全部免费拉进来用**，让整个行业在这套软件上 **派单 / 抢单 / 管理客户 / 管理员工**，之后再对外卖这套软件。
- **行业痛点**：**私单**。这是整条产品线的价值锚点——只要能让老板「看得见每一单、看得见每一笔钱」，软件就有不可替代性。

### 0.2 优先级（老板 2026-09-20 拍板，从高到低）

1. **方便快捷的抢单** —— 陪玩抢单要快，不能慢、不能卡、不能多点两下
2. **管理客户** —— 客户信息一眼看清，改资料不用翻三层
3. **呼叫搭档** —— 双陪单要能把搭档喊来，且对方不能装看不见
4. **统计准确** —— 数字对得上，老板敢拿它发工资
5. **报账系统稳定** —— 报账不能丢单、不能错账
6. **防止私单** —— 收钱不报账能被发现
7. **多店扩张 / 对外出售** —— 中期目标，见 §2.3

**AI 自主判断规则（据此自行决定「该不该做、先做哪个」）**：

- 两件事冲突时，**永远先做编号小的**。
- 任何改动只要让「抢单更慢」或「页面更乱」，**一律不做**，哪怕技术上更先进。
- 凡是能减少点击次数、减少横向拖动、让老板/客服少问一句的改动，**默认值得做**。
- 老板原话：「我不管你任何操作，我只希望第一方便快捷，第二页面整洁。」

### 0.3 铁律（违反即事故）

1. **不影响正在接单的陪玩**。发版、改配置、重启客户端，正在服务中的陪玩一律跳过，等服务结束再更新。
2. **危险功能默认关闭**，打开必须二次确认，并且必须有一键止血（能立刻关掉并让客户端当场生效，不能等重连）。
3. **不能静默生效**。任何会动到陪玩电脑上进程、文件、网络的功能（黑名单等），必须让相关人看得见「谁开的、什么时候开的、影响了谁」。
4. **改完必复查**。交付前必须有可验证证据（线上实测数据 / 截图 / 接口返回），不接受「应该好了」。
5. **提交与发布不需要先问**（前提是不违反铁律 1）；但提交信息里要写清楚这次夹带了哪些工作区里的其它改动。---

## 1. 初衷与七大痛点

系统的出发点不是「做个后台管理」，而是**用软件把陪玩工作室里管不住的地方管住**。原始七大痛点（V30.0 原表）与今天的落地状态：

| # | 痛点 | 对策 | 现状 |
|---|------|------|------|
| 1 | 陪玩开机自己打游戏 / 刷视频，不聊客户 | **流水门槛解锁抢单池**：月流水不到阈值，抢单池不给看，倒逼先去服务老客户 | 🟡 功能有，但线上阈值被设成 `0`（全开）→ 见 §11.2 |
| 2 | 私域维护差，只靠新单 | 首单 / 续单 / 复购客户自动识别 + 续单话术引导 | ✅ 已上线 |
| 3 | 工作微信加多了封号 | 统一分配工作微信、陪玩与微信绑定、离职交接 | ✅ 已上线（#3 的工作微信分配 + 换绑 + 离职交接） |
| 4 | **私单收款不报账** | 强制战报截图 + 金额必填 + 低流水预警 + 订单隐私隔离 | ✅ 主体已上线，仍在加固 → 见 §5 |
| 5 | 存单冲业绩后跑路 | 存单全额计业绩，但**提成打完才释放** | ✅ 已上线（存单 / 预留 / 可支取余额口径） |
| 6 | 双陪搭档沟通靠吼 | 搭档内部对话 + 一键呼叫 + 语音通话 | ✅ 已上线（指定邀请 / 广播找搭档 / WebRTC 语音） |
| 7 | 陪玩不了解客户，私域维护效率低 | 客户画像 + AI 分析 + 个性化话术 | 🟡 画像与话术已上线；**AI 引擎当前不可用**（见 §11.5） |

### 1.1 由此派生、但同样算「初衷」的三件事

- **呼叫搭档要能炸到人**（2026-09-19 追加）：客服在群里问「某某单接不接」，很多陪玩根本不看消息 —— 所以要有**群聊广播**，管理端在群聊里发，**每个陪玩端都要弹窗，5 秒后自动消失**，用 Windows 系统弹窗（Electron 自带通知不可靠）。已上线。
- **广播 = 右下角弹窗；入池 = 不弹窗进派单池**（2026-09-19 拍板）：客服发单时选「广播」走弹窗抢单，选「入池」只静静进订单池。语义**必须保持**，不允许再改回混用。
- **对外卖软件**（2026-09-20 追加）：产品要能复制到别人的店。这条决定了所有功能必须**多店隔离、可配置、零硬编码**。

## 2. 角色、权限与多租户

### 2.1 角色

| 角色 | 代码 | 数量 | 数据范围 |
|------|------|------|----------|
| 超级管理员 / 老板 | `OWNER` | 1~2 人 | 全部门店全部数据（盈亏统计需二级密码） |
| 店长 / 管理员 | `ADMIN` | 每店 1 人 | 本门店全部数据 |
| 租客（租赁店店长） | `ADMIN` + 租赁店 | 每店 1 人 | 本店数据 + 授权管理 |
| 客服 | `CS` | 每店 1~3 人 | 本店订单 + 监控（**客户端需老板授权**） |
| 陪玩 | `COMPANION` | 若干 | 仅本人数据与操作 |

### 2.2 权限要点（易错处，必须守住）

- **老板端**看所有门店；**店长端**只看本店；**陪玩端**只看自己的客户与收入。
- **客服 / 陪玩的客户端必须老板授权后才能登录**（授权管理页）。
- **盈亏统计需要二级密码**。
- **陪玩看不到客户的微信号 / 收款码**，除非该客户由他本人服务（防私单的核心机制，见 §5）。
- 桥接工作室的陪玩能看到本店订单池里的单，但**客户联系方式依然不可见**。
- **陪玩可以自己发单**（2026-09-20 拍板）：陪玩端保留「发布订单」入口。
  早先 V30.0 文档里「陪玩不能发单」的权限表**作废**，以本条为准。

### 2.3 多租户与对外出售（中期规划）

现状：多店隔离（`studioId` 隔离）已经可用，直营店 + 租赁店都跑在一套系统上。

**要对外卖，还差这几块（目前只有雏形，尚无实现，需单独规划）**：

- 自助开户 / 建店：客户自己注册一家店并成为店长，不用开发者手工开
- 计费与续期：免费期策略、到期停用、套餐/席位
- 数据隔离验收：给第三方用之前，必须有一次「跨店越权」全量回归
- 白标：店名 / LOGO / 话术可替换，不能让客户看见「蠢驴」
- 先免费策略：**所有线下陪玩店免费先用** —— 所以免费期开关、用量上限、拉新统计要能一键控制---

## 3. 核心业务闭环

### 3.1 一单是怎么走完的

```
客服/店长/老板 发布订单
        │
        ├── 选「广播」→ 目标陪玩端右下角弹窗（秒级），点同意即抢单
        └── 选「入池」→ 不弹窗，静静进「订单池」，按段位分段可见
                    │
            陪玩抢单成功（先到先得，只有一个人能抢到）
                    │
        ┌───────────┴────────────┐
    单人单                      双陪单
        │                        └── 呼叫搭档（指定 / 广播找人）
        │                              └── 搭档接单 → 搭档端进入服务
        └───────────┬────────────┘
                开始服务（计时 / 状态变「接单中」）
                    │
                结束服务 → 战报截图 + 客户信息 + 金额
                    │
                服务结算 → 业绩入账 → 可支取余额更新
```

### 3.2 发布订单（管理端 / 客服端）

- **发布入口**：客服工作台、管理端「上传订单」、**陪玩端订单池**（陪玩自己拉到的客户可直接建单）。
- **发布即选方式**：
  - **广播** = 右下角弹窗抢单，**快**，适合急单、需要马上有人接的单。
  - **入池** = 不弹窗，进订单池，按 §3.3 的分段顺序慢慢放出来。
- 必须带：订单类型（即时 / 预约）、时长、金额、客户（或新客户信息）、来源渠道、备注。
- **客户端与页面都能发**，发布按钮在客服最顺手的位置。

### 3.3 订单池的可见顺序（关键规则，别改错）

订单进入订单池后，**不是所有人同时看到**，按这个顺序逐段放出来（线上实际配置，单位：秒）：

| 段位 / 对象 | 延迟 | 说明 |
|-------------|------|------|
| 本店 **上等马** | **0 秒** | 立即看到 |
| 本店 **中等马** | **60 秒** | 上等马没抢才轮到 |
| 本店 **下等马** | **120 秒** | |
| **桥接工作室**（如光耀电竞） | **300 秒** | 5 分钟后才炸过去，本店有 5 分钟先手 |
| **租赁店** | **300 秒** | |
| 老板端 / 发单的客服店长 | **0 秒** | 自己发的单不受段位延迟影响 |

- **顺序不可打乱**：「上等马 → 桥接 → 中等马 → 下等马」的业务意图是「好马先吃」，桥接是补位而不是抢位。
- **桥接工作室目前是「一刀切 5 分钟」**，不区分上等马 / 中等马 —— 是否要分层见 §11.4。
- **订单池排序：新发布的单永远在最上面**（按发布时间倒序）。历史上出现过「新单跑到最底部」，属于回归缺陷，任何人改动订单池都要回归这一点。
- **弹窗前会复查**：这单是否还在、是否已被抢走 / 被客服认领。已在别人的单不会再弹，**不弹废单**。

### 3.4 抢单

- **先到先得**，一单只能被一个人抢到，抢单接口必须原子化，不能出现「两个人都抢到」。
- 抢单是**一键**的：弹窗上直接「同意」，订单池列表上直接「抢单」，不要求先点详情。
- **抢到订单后直接跳转到「订单管理」**；陪玩点「添加成功」后**直接跳转到「客户管理」**（2026-09-19 明确要求：抢完就干活，不要让人自己找路）。
- 抢到双陪单 → 立刻进入「呼叫搭档」（见下）。

### 3.5 呼叫搭档（双陪单）

- 两条路：**指定搭档**（点人名直接叫）/ **广播找搭档**（在群里喊，谁都能应）。
- **被叫的人不能装看不见**：搭档邀请要有明显提醒；超时未响应、被拒绝，**都要通知发起人**。
- 搭档接单后，搭档端进入服务界面；**搭档看不到客户微信 / 收款码**（防私单）。
- 服务中搭档之间可以用**语音通话**（WebRTC）。

### 3.6 服务与结算

- **开始服务**：陪玩点开始，状态变「接单中」，开始计时。
- **结束服务**：必须填 **战报截图 + 客户 + 金额**，否则不允许结束（这是防私单的第一道闸）。
- **结算**：业绩入账 → 更新可支取余额（公式见 §7.1）。
- 结算口径要能说清「这一单是谁家接的、算谁的业绩」。

### 3.7 订单状态机

陪玩侧状态（人员列表按这个顺序分组显示，从上往下）：

> **群聊 → 客服 → 店长 → 在线且空闲的陪玩 → 在线且接单中的陪玩 → 在线且娱乐中的陪玩 → 离线人员**

- **离线的不管是谁，一律排到最后**（2026-09-19 拍板）。客服、店长在线时固定排第 2、3 位，离线时也不许插队在前。
- 群聊、客服、店长的**行宽与样式要跟其它行一致**，不许某个人的行特别宽（曾出现「邵泽慧那一行太宽」）。
- 客户类型自动识别：新客 / 首单 / 续单 / 复购，按订单历史自动判定。

### 3.8 报账

- 四类报账：**新单 / 续单 / 复购 / 打赏**，每类都要：日期 + 收款方式（微信 / 支付宝）+ **客户转账截图上传** + 客户信息（微信号 / 客户编号）。
- 每个陪玩有唯一的**报账码**，用于关联与追溯。
- 日 / 月流水统计：各类单的数量 / 金额 / 占比 + 陪玩当月收入 + 自动排名。
- **报账系统必须稳**（优先级 5）：不许丢单、不许错账；有对账机制（见 `finance-reconciliation` 提案）。
- **流转失败明细必须带时间**（2026-09-19 明确要求）：老板要能一眼看出「这单是什么时候发布的」才能决定要不要再次入池。

### 3.9 客户全生命周期

- 客户档案：编号（钉在左侧，旁边并排显示微信号）+ 昵称 + 来源 + 备注 + 累计消费 + 最近跟进。
- **客户列表所有列宽固定**、**编号列钉左、操作列钉右**、字号统一 —— 「订单发布 → 订单池 → 订单管理 → 客户管理」自始至终是同一份数据，**列宽与字号必须共用一套全局规格**。
- **每条订单 / 客户信息都要能直接点行进详情**，不能逼用户先找「编辑」按钮（订单信息一长，编辑按钮就被挤没了）。
- 客户跟进记录、客户画像字段、AI 建议见 §4.3。
- **删除客户要审核**（防误删、防跑路前清档）。

### 3.10 娱乐计费与工作时长

- **娱乐扣费**：娱乐分钟 × 1 元/分钟；**月流水 ≥ 300 元免单**（线上当前费率被设为 0，即暂不扣费 → 见 §11.3）。
- **接单率** = 接单时长 ÷ 在线时长；在线时长按心跳累计（考勤）。
- 陪玩状态切换必须真实反映「在干嘛」，这是接单率与考勤的基础数据。---

## 4. 四端功能清单与现状

| 陪玩绩效看板 | 接单率 / 续单率 / 复购率排行 | ✅ |
| 订单管理 | 全部订单、状态、**接单陪玩**、异常处理 | ✅ |
| 订单管理 · 接单工作室 | 列表里要能直接看出「这单是谁家接的」，不用去每日统计翻 | ⚪ 待做（老板已确认要） |
| 上传订单 | 手动录入 / 发布订单 | ✅ |
| 订单池（派单工作台） | 分段可见、抢单、流转失败明细（**带发布时间**） | ✅ |
| 陪玩管理 | 资料、段位、工作微信、状态 | ✅ |
| 陪玩离职处理 | 客户与工作微信交接 | ✅ |
| 报账与财务 | 报账单审核、支取审核、月底结算 | ✅ |

## 5. 防私单（行业痛点，最高价值）

老板原话：**私单是这个行业的痛点**。所以防私单不是「一个功能」，而是贯穿全系统的一组机制。它直接决定了这款软件对外卖的时候值不值钱。

### 5.1 已上线（8 条）

1. **客户联系方式隔离**：非本人服务的陪玩看不到客户微信号 / 收款码（`order-privacy`）。
2. **结束服务必须交证据**：战报截图 + 客户 + 金额，缺一不可。
3. **报账码关联追溯**：每人唯一报账码，报账单与订单可对账。
4. **低流水预警**：流水低于阈值（线上 300）触发预警，专盯「明明在接单却没流水」的人。
5. **存单预留**：存单全额计业绩，但提成打完才释放（防冲完成绩跑路）。
6. **客户删除要审核**：防止跑路前清档、防止误删。
7. **工作微信统一分配 + 离职交接**：微信是资产不是个人物品，离职必须交回。
8. **跨店/桥接订单可追溯**：桥接工作室接的单在两侧都能看到。

### 5.2 待补（5 条，按性价比排序）

1. **订单 / 客户列表增加「接单工作室」列或标签**（老板已确认要，成本最低，先做）。
2. **报账金额与订单金额偏差预警**：收 500 报 200 时立刻标红。
3. **客户微信被改绑预警**：客户原本绑在 A 的微信，突然被改成 B 的微信 → 报警。
4. **跨店撞单检测**：同一个客户在不同店 / 不同陪玩名下重复出现 → 大概率是私单搬运。
5. **陪玩端敏感操作留痕**（截图导出 / 剪贴板复制客户微信）—— 涉及监控，需老板单独拍板后做。

## 6. 客户端与电脑管控

- **客户端形态**：Electron 桌面客户端（客服端 / 陪玩端），支持**自动更新**：发布后 5 分钟内所有在线端自动更新并重启，**正在接单的自动跳过**，等服务结束再更新。
- **心跳与在线时长**：客户端定时心跳，累计在线时长，作为接单率与考勤的分母。
- **进程黑名单**（管「陪玩开机自己打游戏」）：
  - 有**总开关** `blacklist.auto_kill`（进程黑名单页顶部），**拨动即生效、当场下发给所有客户端**，关掉时下发空名单，连没升级的老客户端也会立刻停下。
  - **状态黑名单**：按状态限制进程。当前线上只有一条：**空闲 → 三角洲行动**（即「空闲时不许跑三角洲」）；「娱乐中 → python.exe」是 8 月 30 日测试遗留，**已删除**。
  - 打开总开关会弹**二次确认**，并提示会踢掉正在玩的游戏。
  - **历史教训（必须记住）**：曾出现「宋树祥 / 徐建业 的游戏突然掉了」——原因是黑名单被打开且静默生效。所以：**危险功能默认关 + 二次确认 + 一键止血 + 影响可见**，四条缺一不可。
- **管理员远程指令**：管理端可向客户端推送指令（需客户端主进程 WebSocket 在线）。这条链路现在还在排查（本机那台客户端主进程 WebSocket 曾整天连不上），排查结论要回填本文。---

## 7. 统计与财务口径

### 7.1 公式（唯一口径，任何页面都必须用这一套）

| 指标 | 公式 |
|------|------|
| 接单率 | 接单时长 ÷ 在线时长 × 100% |
| 续单率 | 续单订单数 ÷ 总服务订单数 × 100% |
| 复购率 | 复购客户数 ÷ 总服务客户数 × 100% |
| 首单占比 | 首单金额 ÷ 月总流水 × 100% |
| 续单占比 | 续单金额 ÷ 月总流水 × 100% |
| 复购占比 | 复购金额 ÷ 月总流水 × 100% |
| **可支取余额** | **(当月累计业绩 × 50%) − 已支取 − 未打存单预留** |
| 娱乐扣费 | 娱乐分钟 × 1 元/分钟（月流水 ≥ 300 元免单） |

### 7.2 分润阶梯（**口径不一致，必须拍板**）

- **代码默认值**（`revenue-calculator.ts`）：< 5200 → 五五；5200 ~ 10000 → 六四；≥ 10000 → 七三；**七三需满 6 个月工龄**（老员工可豁免）。
- **线上实际配置**：< 6000 → 五五；6000 ~ 10000 → 六四；≥ 10000 → 七三。
- **冲突点**：**5200 还是 6000**。发工资用的就是这个数字，必须老板拍一次，改完两边一起改（代码默认值 + 线上配置），见 §11.1。

### 7.3 统计的硬要求

- **准确**（优先级 4）：老板敢拿它发工资。任何统计口径的变化都要在 CHANGELOG 里写清楚，并核对历史数据会不会被改写。
- **能看到时间**：每一笔订单、每一条流转失败明细，都必须显示**发布时间**（老板要靠它决定要不要再次入池）。
- **能看到归属**：每单要能看出「哪个陪玩接的」以及「哪个工作室接的」。
- **能对账**：报账金额 vs 订单金额 vs 收款截图，三者要能互相校验（见 §5.2）。

## 8. 非功能需求

- **方便快捷**（第一优先）：常用操作必须一屏内完成；能一键的不要两步；抢单路径最短。
- **页面整洁**（第二优先）：列宽、字号、间距统一（全局规格）；钉左钉右解决横向拖动看不全的问题；不允许出现「某一行特别宽 / 某个人样式不一样」。
- **稳定性**：报账、结算、统计不允许出错；服务端发布要能随时回滚。
- **安全**：密码只存 bcrypt（**老板也不应该能直接看到明文，只能重置**——这是有意与早期文档不一样的地方）；JWT 双 token；跨店数据隔离。
- **可运维**：客户端自动更新（不影响接单）；危险开关一键止血；关键配置进 `SystemConfig` 可热改，不硬编码。
- **可复制**：这套系统要能卖给别人的店，所以任何「只对蠢驴有效」的硬编码都是技术债。
